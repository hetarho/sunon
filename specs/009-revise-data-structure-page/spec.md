# Feature Specification: 데이터 구조 페이지 개편

**Feature Branch**: `009-revise-data-structure-page`  
**Created**: 2026-04-07  
**Status**: Draft  
**Input**: User description: "007 엔티티 페이지 스펙을 전면 수정. 기획자 친화적으로, 구조적 사고를 도와주는 수준. float 같은 개발 타입 제거. 표 형태로 자연어 표기 (속성명 | 속성 정보)."
**Supersedes**: `007-entity-page` — 개발자 중심 데이터 모델링 → 기획자 중심 데이터 구조 정리로 방향 전환

## 배경 및 방향

기존 007-entity-page는 DB 설계 도구에 가까웠다. `int`, `float`, `bool`, `isList`, `required` 같은 개발 용어를 사용하고, 타입 드롭다운과 체크박스로 구성되어 있어 기획자가 접근하기 어렵다.

이번 개편의 핵심 방향:
- **"엔티티"라는 용어를 기획자에게 친숙한 용어로 교체**한다.
- **개발 타입(int, float, bool 등)을 완전히 제거**하고, 속성 정보를 자연어로 기술한다.
- **표 형태(속성명 | 속성 정보)**로 직관적으로 데이터 구조를 정리할 수 있게 한다.
- 기획자가 "이 서비스에서 다루는 데이터가 뭐고, 각 데이터에는 어떤 정보가 있는지"를 구조적으로 정리할 수 있도록 돕는 것이 목표다.

## 용어 변경

| 기존 (007) | 변경 후 (009) | 이유 |
|------------|--------------|------|
| Entity | 데이터 항목 (Data Item) | "엔티티"는 개발 용어. "데이터 항목"은 기획자가 직관적으로 이해 가능 |
| Column | 속성 (Attribute) | "칼럼"은 DB 용어. "속성"은 기획 문서에서 자연스러움 |
| Type (int, float...) | 속성 정보 (자연어 설명) | 개발 타입 대신 자연어로 "어떤 값이 들어가는지" 설명 |
| isList | 제거 | 개발 개념. 필요 시 속성 정보에 자연어로 기술 |
| required | 제거 | 개발 개념. 필요 시 속성 정보에 자연어로 기술 |
| Local Type / Enum | 제거 | 기획 단계에서 불필요한 개발 구조 |

## User Scenarios & Testing

### User Story 1 - 데이터 항목 목록 조회 (Priority: P1)

사용자가 프로젝트 사이드바에서 "데이터 구조" 메뉴를 클릭하면, 해당 프로젝트에서 정의한 데이터 항목 목록이 표시된다. 예를 들어 쇼핑몰 기획이라면 "회원", "상품", "주문" 같은 항목이 리스트로 나타난다.

**Why this priority**: 데이터 항목 목록을 확인하는 것이 모든 데이터 구조 관련 작업의 진입점이다.

**Independent Test**: 데이터 구조 메뉴 클릭 후 기존에 생성된 데이터 항목들이 리스트로 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 프로젝트에 데이터 항목이 존재할 때, **When** 사이드바에서 데이터 구조 메뉴를 클릭하면, **Then** 각 데이터 항목 이름이 리스트로 표시된다.
2. **Given** 프로젝트에 데이터 항목이 없을 때, **When** 데이터 구조 메뉴를 클릭하면, **Then** 빈 상태 안내와 "데이터 항목 추가" 버튼이 표시된다.
3. **Given** 데이터 항목 리스트가 표시된 상태에서, **When** 특정 항목을 클릭하면, **Then** 해당 항목의 상세 페이지로 이동한다.

---

### User Story 2 - 데이터 항목 추가 (Priority: P1)

사용자가 "데이터 항목 추가" 버튼을 클릭하면 이름 입력 모달이 나타난다. 이름을 입력하고 생성하면 새 데이터 항목이 만들어진다.

**Why this priority**: 데이터 항목 생성은 데이터 구조 정리의 첫 단계이며, 이후 속성 추가의 전제 조건이다.

**Independent Test**: 추가 버튼 → 모달에서 이름 입력 → 생성 클릭 후, 리스트에 새 항목이 나타나는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 데이터 구조 페이지에서, **When** "데이터 항목 추가" 버튼을 클릭하면, **Then** 이름 입력 모달이 표시된다.
2. **Given** 모달에서 유효한 이름을 입력한 상태에서, **When** 생성 버튼을 클릭하면, **Then** 새 데이터 항목이 생성되고 리스트에 추가된다.
3. **Given** 이미 존재하는 이름을 입력한 상태에서, **When** 생성 버튼을 클릭하면, **Then** 중복 이름 오류가 표시된다.
4. **Given** 빈 이름으로 생성을 시도하면, **Then** 이름 필수 입력 안내가 표시된다.

---

### User Story 3 - 데이터 항목 상세 페이지에서 속성 관리 (Priority: P1)

사용자가 데이터 항목 상세 페이지에서 속성을 추가, 편집, 삭제할 수 있다. 각 속성은 **속성명**과 **속성 정보** 두 칸으로 구성된 표 형태로 표시된다. 속성 정보는 자연어로 자유롭게 작성한다.

예시 — "회원" 데이터 항목:

| 속성명 | 속성 정보 |
|--------|----------|
| 이름 | 회원의 실명 |
| 이메일 | 로그인에 사용되는 이메일 주소 |
| 가입일 | 회원이 가입한 날짜 |
| 등급 | 일반, 실버, 골드, VIP 중 하나 |
| 보유 쿠폰 | 현재 사용 가능한 쿠폰 목록 |

**Why this priority**: 속성 정의는 데이터 구조 페이지의 핵심 가치이다. 기획자가 "이 데이터에 어떤 정보가 들어가는지"를 자유롭게 정리할 수 있어야 한다.

**Independent Test**: 상세 페이지에서 속성을 추가하고, 속성명과 속성 정보를 입력한 뒤 저장이 잘 되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 데이터 항목 상세 페이지에 진입했을 때, **When** 기존 속성이 있으면, **Then** "속성명 | 속성 정보" 표 형태로 표시된다.
2. **Given** 상세 페이지에서, **When** "속성 추가" 버튼을 클릭하면, **Then** 새 행이 추가되어 속성명과 속성 정보를 입력할 수 있다.
3. **Given** 속성 정보를 입력하거나 수정한 상태에서, **When** 일정 시간이 경과하면, **Then** 변경 내용이 자동 저장된다.
4. **Given** 속성이 존재하는 상태에서, **When** 삭제 버튼을 클릭하면, **Then** 해당 속성이 제거되고 자동 저장된다.
5. **Given** 상세 페이지에서, **When** 뒤로가기 버튼을 클릭하면, **Then** 데이터 항목 리스트로 돌아간다.

---

### User Story 4 - 데이터 항목 삭제 (Priority: P2)

사용자가 데이터 항목 리스트에서 특정 항목을 삭제할 수 있다. 삭제 시 확인 다이얼로그가 표시되며, 확인하면 해당 항목이 삭제된다.

**Why this priority**: 잘못 생성한 항목을 정리할 수 있어야 하지만, 생성/조회/편집보다 사용 빈도가 낮다.

**Independent Test**: 리스트에서 삭제 → 확인 → 항목 삭제 및 리스트 갱신을 확인한다.

**Acceptance Scenarios**:

1. **Given** 데이터 항목 리스트에서, **When** 삭제 버튼을 클릭하면, **Then** 삭제 확인 다이얼로그가 표시된다.
2. **Given** 확인 다이얼로그에서, **When** 확인을 클릭하면, **Then** 해당 항목이 삭제되고 리스트에서 제거된다.
3. **Given** 확인 다이얼로그에서, **When** 취소를 클릭하면, **Then** 아무 변경도 발생하지 않는다.

---

### Edge Cases

- 데이터 항목 이름에 파일 시스템에서 허용되지 않는 특수문자가 포함된 경우 유효성 검사에서 거부한다.
- 데이터 구조 디렉토리가 존재하지 않는 프로젝트에서는 자동으로 디렉토리를 생성한다.
- md 파일이 예상과 다른 형식으로 작성된 경우 파싱 가능한 부분만 표시하고 나머지는 보존한다.

## Requirements

### Functional Requirements

- **FR-001**: 시스템은 프로젝트의 데이터 구조 디렉토리를 스캔하여 데이터 항목 목록을 표시해야 한다.
- **FR-002**: 시스템은 "데이터 항목 추가" 버튼을 제공하여 새 항목 생성 모달을 열 수 있어야 한다.
- **FR-003**: 시스템은 모달에서 입력된 이름으로 데이터 항목 파일을 생성해야 한다.
- **FR-004**: 시스템은 중복 이름 및 빈 이름에 대한 유효성 검사를 수행해야 한다.
- **FR-005**: 시스템은 데이터 항목 상세 페이지에서 속성(속성명, 속성 정보)을 추가, 편집, 삭제할 수 있어야 한다.
- **FR-006**: 속성 입력 시 표 형태(속성명 | 속성 정보)로 표시하며, 속성 정보는 자연어 텍스트로 자유롭게 입력한다. 개발 타입 드롭다운이나 체크박스는 제공하지 않는다.
- **FR-007**: 시스템은 속성 변경 시 디바운스 방식으로 자동 저장해야 한다.
- **FR-008**: 시스템은 데이터 구조 디렉토리가 없는 경우 자동으로 생성해야 한다.
- **FR-009**: 시스템은 항목 이름에 포함된 파일 시스템 비허용 문자를 검증하고 거부해야 한다.
- **FR-010**: 시스템은 리스트에서 삭제 기능을 제공하며, 확인 다이얼로그 후 해당 항목을 삭제해야 한다.

### 마크다운 저장 형식

데이터 항목 파일은 다음 구조를 따른다:

```
# 회원

## 속성

| 속성명 | 속성 정보 |
|--------|----------|
| 이름 | 회원의 실명 |
| 이메일 | 로그인에 사용되는 이메일 주소 |
| 가입일 | 회원이 가입한 날짜 |
| 등급 | 일반, 실버, 골드, VIP 중 하나 |
| 보유 쿠폰 | 현재 사용 가능한 쿠폰 목록 |
```

- 최상위 `# ` 헤딩은 데이터 항목 이름이다.
- `## 속성` 섹션은 마크다운 테이블 형식으로 속성을 정의한다.
- 테이블 헤더는 `속성명`, `속성 정보`로 고정한다.
- **속성 정보는 자연어 텍스트**이며, 개발 타입(int, float, bool 등)을 사용하지 않는다.
- 기획자가 자유롭게 "어떤 값인지"를 설명하는 방식으로 작성한다.
- `## 속성` 외의 `## ` 섹션은 파싱하지 않고 원본 그대로 보존한다.

### 기존 007 대비 제거되는 개념

- 데이터 타입 드롭다운 (int, string, float, bool, datetime, text)
- isList 체크박스 (배열 여부)
- required 체크박스 (필수 여부)
- Local Type (하위 구조체)
- Local Enum (열거형)
- types/ 디렉토리

### Key Entities

- **데이터 항목**: 서비스에서 다루는 데이터의 단위. 이름을 가지며 여러 속성을 포함한다. 하나의 md 파일에 대응한다.
- **속성**: 데이터 항목을 구성하는 정보. 속성명과 속성 정보(자연어 설명)로 구성된다.

## Success Criteria

### Measurable Outcomes

- **SC-001**: 사용자가 데이터 구조 메뉴 클릭 후 1초 이내에 데이터 항목 리스트를 확인할 수 있다.
- **SC-002**: 사용자가 이름 입력 후 10초 이내에 새 데이터 항목을 생성할 수 있다.
- **SC-003**: 속성 추가/편집/삭제 후 자동 저장이 완료되어 파일에 반영된다.
- **SC-004**: 저장된 파일을 외부 편집기에서 열었을 때 사람이 읽을 수 있는 구조화된 마크다운 형식이 유지된다.
- **SC-005**: 기획자가 별도의 가이드 없이 데이터 항목과 속성을 직관적으로 추가할 수 있다 (개발 용어에 대한 사전 지식 불필요).

## Assumptions

- 기존 007-entity-page의 코드를 이 스펙 기준으로 리팩터링한다 (신규 파일 생성이 아닌 기존 코드 수정).
- 디렉토리명을 `entities/`에서 `data/`로 변경한다. 기존 프로젝트의 `entities/` 디렉토리는 마이그레이션하지 않는다 (기존 데이터는 새 UI에서 접근 불가, 새 프로젝트만 `data/` 사용).
- 기존 Product 페이지와 동일한 디바운스 자동 저장 패턴(500ms)을 따른다.
- 항목 이름은 파일명으로 사용되므로 영문, 숫자, 한글, 밑줄, 하이픈, 공백을 허용한다.
- 사이드바 메뉴명은 "Entities" 에서 기획자 친화적 이름으로 변경한다.
