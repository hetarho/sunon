# Feature Specification: Policy 페이지

**Feature Branch**: `010-policy-page`  
**Created**: 2026-04-07  
**Status**: Draft  
**Input**: User description: "Policy 페이지 구현: 의사결정 기준을 자유 형식 마크다운으로 작성/관리하는 페이지. policies/{name}.md 플랫 구조, 제목만 필수, 본문 자유 형식."

## 배경 및 방향

Policy는 프로덕트의 의사결정 기준을 정리하는 레이어다. "~할 때 ~한다" 형태의 규칙으로, 이후 spec 생성 시 빈틈 없는 명세를 만들기 위한 재료가 된다.

핵심 방향:
- **최소한의 제약**: 제목(`# `)만 필수, 본문은 자유 형식 마크다운
- **플랫 구조**: 카테고리 분류 없이 `policies/{name}.md` 형태로 저장
- **기획자 친화적**: 데이터 항목 페이지(009)와 동일한 UX 패턴 (목록 → 상세 → 편집)
- 기존 README의 카테고리(ux, data, validation, formatting, system) 분류는 UI에서 강제하지 않음. 필요 시 본문에 자유롭게 기술

## User Scenarios & Testing

### User Story 1 - Policy 목록 조회 (Priority: P1)

사용자가 프로젝트 사이드바에서 "Policies" 메뉴를 클릭하면, 해당 프로젝트에서 정의한 policy 목록이 표시된다. 예를 들어 "이메일 형식 검증", "미성년자 가입 제한", "가격 표시 기준" 같은 항목이 리스트로 나타난다.

**Why this priority**: Policy 목록 확인이 모든 policy 관련 작업의 진입점이다.

**Independent Test**: Policies 메뉴 클릭 후 기존에 생성된 policy들이 리스트로 표시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 프로젝트에 policy 파일이 존재할 때, **When** 사이드바에서 Policies 메뉴를 클릭하면, **Then** 각 policy 이름이 리스트로 표시된다.
2. **Given** 프로젝트에 policy가 없을 때, **When** Policies 메뉴를 클릭하면, **Then** 빈 상태 안내와 "Policy 추가" 버튼이 표시된다.
3. **Given** Policy 리스트가 표시된 상태에서, **When** 특정 항목을 클릭하면, **Then** 해당 policy의 상세 페이지로 이동한다.

---

### User Story 2 - Policy 추가 (Priority: P1)

사용자가 "Policy 추가" 버튼을 클릭하면 이름 입력 모달이 나타난다. 이름을 입력하고 생성하면 새 policy 파일이 만들어지고 바로 상세 페이지로 이동한다.

**Why this priority**: Policy 생성은 의사결정 기준 정리의 첫 단계이며, 이후 편집의 전제 조건이다.

**Independent Test**: 추가 버튼 → 모달에서 이름 입력 → 생성 클릭 후, 상세 페이지로 이동하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** Policy 목록 페이지에서, **When** "Policy 추가" 버튼을 클릭하면, **Then** 이름 입력 모달이 표시된다.
2. **Given** 모달에서 유효한 이름을 입력한 상태에서, **When** 생성 버튼을 클릭하면, **Then** 새 policy 파일이 생성되고 상세 페이지로 이동한다.
3. **Given** 이미 존재하는 이름을 입력한 상태에서, **When** 생성 버튼을 클릭하면, **Then** 중복 이름 오류가 표시된다.
4. **Given** 빈 이름으로 생성을 시도하면, **Then** 이름 필수 입력 안내가 표시된다.

---

### User Story 3 - Policy 상세 페이지에서 내용 편집 (Priority: P1)

사용자가 policy 상세 페이지에서 자유 형식 마크다운으로 의사결정 기준을 작성한다. 제목 아래 본문 영역에 텍스트를 입력하면 자동 저장된다.

예시 — "이메일 형식 검증" policy:

```markdown
# 이메일 형식 검증

이메일 주소를 입력받을 때, @ 앞뒤로 최소 1자 이상이어야 한다.
허용되지 않는 형식일 경우 "올바른 이메일 주소를 입력해주세요" 메시지를 표시한다.

## 예외
- 소셜 로그인 시에는 이메일 형식 검증을 건너뛴다.
```

**Why this priority**: 본문 편집은 policy 페이지의 핵심 가치이다. 기획자가 의사결정 기준을 자유롭게 정리할 수 있어야 한다.

**Independent Test**: 상세 페이지에서 본문을 입력/수정한 뒤, 파일에 자동 저장되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** Policy 상세 페이지에 진입했을 때, **When** 기존 내용이 있으면, **Then** 상단에 제목 필드, 하단에 본문 에디터가 분리되어 표시된다.
2. **Given** 상세 페이지에서, **When** 본문 에디터에 텍스트를 입력하면, **Then** 자유 형식 마크다운으로 작성할 수 있다.
3. **Given** 내용을 입력하거나 수정한 상태에서, **When** 일정 시간이 경과하면, **Then** 변경 내용이 자동 저장된다.
4. **Given** 상세 페이지에서, **When** 뒤로가기 버튼을 클릭하면, **Then** policy 목록으로 돌아간다.

---

### User Story 4 - Policy 삭제 (Priority: P2)

사용자가 policy 리스트에서 특정 항목을 삭제할 수 있다. 삭제 시 확인 다이얼로그가 표시되며, 확인하면 해당 policy가 삭제된다.

**Why this priority**: 잘못 생성한 policy를 정리할 수 있어야 하지만, 생성/조회/편집보다 사용 빈도가 낮다.

**Independent Test**: 리스트에서 삭제 → 확인 → 항목 삭제 및 리스트 갱신을 확인한다.

**Acceptance Scenarios**:

1. **Given** Policy 리스트에서, **When** 삭제 버튼을 클릭하면, **Then** 삭제 확인 다이얼로그가 표시된다.
2. **Given** 확인 다이얼로그에서, **When** 확인을 클릭하면, **Then** 해당 policy가 삭제되고 리스트에서 제거된다.
3. **Given** 확인 다이얼로그에서, **When** 취소를 클릭하면, **Then** 아무 변경도 발생하지 않는다.

---

### User Story 5 - Policy 이름 변경 (Priority: P2)

사용자가 policy 상세 페이지에서 제목을 수정하면 파일명도 함께 변경된다.

**Why this priority**: 초기에 이름을 잘못 지었을 때 수정할 수 있어야 하지만, 핵심 흐름은 아니다.

**Independent Test**: 상세 페이지에서 제목 수정 후 파일명이 변경되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** Policy 상세 페이지에서, **When** 제목을 수정하면, **Then** 변경된 이름으로 파일이 리네임된다.
2. **Given** 이미 존재하는 이름으로 변경하려 할 때, **Then** 중복 이름 오류가 표시되고 변경이 취소된다.

---

### Edge Cases

- Policy 이름에 파일 시스템에서 허용되지 않는 특수문자가 포함된 경우 유효성 검사에서 거부한다.
- policies 디렉토리가 존재하지 않는 프로젝트에서는 첫 policy 생성 시 자동으로 디렉토리를 생성한다.
- md 파일에 `# ` 헤딩이 없는 경우 파일명을 제목으로 사용하여 표시한다.
- 외부 편집기에서 수정된 md 파일도 정상적으로 읽어와 표시한다.

## Requirements

### Functional Requirements

- **FR-001**: 시스템은 프로젝트의 `policies/` 디렉토리를 스캔하여 policy 목록을 표시해야 한다.
- **FR-002**: 시스템은 "Policy 추가" 버튼을 제공하여 이름 입력 모달을 열 수 있어야 한다.
- **FR-003**: 시스템은 모달에서 입력된 이름으로 policy 파일(`policies/{name}.md`)을 생성해야 한다.
- **FR-004**: 시스템은 중복 이름 및 빈 이름에 대한 유효성 검사를 수행해야 한다.
- **FR-005**: 시스템은 policy 상세 페이지에서 제목 필드(별도 텍스트 필드)와 본문 영역(텍스트 에디터)을 분리하여 제공해야 한다.
- **FR-006**: 제목 필드는 필수 입력이며, 본문은 자유 형식 마크다운으로 작성한다.
- **FR-007**: 시스템은 내용 변경 시 디바운스 방식으로 자동 저장해야 한다.
- **FR-008**: 시스템은 `policies/` 디렉토리가 없는 경우 첫 생성 시 자동으로 디렉토리를 생성해야 한다.
- **FR-009**: 시스템은 파일명에 포함된 파일 시스템 비허용 문자를 검증하고 거부해야 한다.
- **FR-010**: 시스템은 리스트에서 삭제 기능을 제공하며, 확인 다이얼로그 후 해당 policy를 삭제해야 한다.
- **FR-011**: 시스템은 상세 페이지에서 제목 변경 시 파일명을 함께 리네임해야 한다.

### 마크다운 저장 형식

Policy 파일은 다음 구조를 따른다:

```
# 이메일 형식 검증

이메일 주소를 입력받을 때, @ 앞뒤로 최소 1자 이상이어야 한다.
허용되지 않는 형식일 경우 "올바른 이메일 주소를 입력해주세요" 메시지를 표시한다.

## 예외
- 소셜 로그인 시에는 이메일 형식 검증을 건너뛴다.
```

- 최상위 `# ` 헤딩은 policy 이름이다 (필수).
- `# ` 이후의 모든 내용은 자유 형식 마크다운 본문이다.
- 본문에 `## `, 목록, 표, 코드블록 등 어떤 마크다운 문법이든 사용 가능하다.
- 시스템은 `# ` 헤딩만 파싱하고, 나머지 본문은 있는 그대로 저장/표시한다.

### Key Entities

- **Policy**: 프로덕트의 의사결정 기준. 이름(제목)과 자유 형식 본문으로 구성된다. 하나의 md 파일에 대응한다.

## Success Criteria

### Measurable Outcomes

- **SC-001**: 사용자가 Policies 메뉴 클릭 후 1초 이내에 policy 리스트를 확인할 수 있다.
- **SC-002**: 사용자가 이름 입력 후 10초 이내에 새 policy를 생성하고 편집을 시작할 수 있다.
- **SC-003**: 본문 편집 후 자동 저장이 완료되어 파일에 반영된다.
- **SC-004**: 저장된 파일을 외부 편집기에서 열었을 때 사람이 읽을 수 있는 마크다운 형식이 유지된다.
- **SC-005**: 기획자가 별도의 가이드 없이 policy를 직관적으로 추가하고 작성할 수 있다.

## Assumptions

- 데이터 항목 페이지(009)와 동일한 UX 패턴(목록 → 상세 → 자동 저장)을 따른다.
- 디렉토리명은 `policies/`이며, 카테고리별 하위 디렉토리는 사용하지 않는다.
- 기존 Product 페이지, 데이터 항목 페이지와 동일한 디바운스 자동 저장 패턴(500ms)을 따른다.
- 이름은 파일명으로 사용되므로 영문, 숫자, 한글, 밑줄, 하이픈, 공백을 허용한다.
- 사이드바 메뉴의 "Policies" 항목은 이미 존재하며, 플레이스홀더를 실제 페이지로 교체한다.
- 본문 편집은 일반 텍스트 에디터 형태이며, 마크다운 실시간 프리뷰는 제공하지 않는다.
